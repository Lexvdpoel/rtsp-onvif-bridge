Adds a second ONVIF profile, which lets an NVR pick a low-resolution stream for previews.
The virtual MAC is derived from this, so deleting this camera and adding it back later gives the same address and your DHCP reservation still fits. Left empty, the host and path of the source URL are used instead — that survives a password change but not the camera moving to a different IP. Fill it in when you add the camera: the virtual MAC is fixed on creation and is not recalculated afterwards.

Stream handling
How this camera reads its own source. TCP is the safe choice across a router.
Leave this on both unless an NVR picks badly. Narrowing it to TCP stops the relay opening a UDP listener at all, which fixes an NVR that chooses UDP over a routed network — and breaks one that reads TCP poorly. Multicast is never offered.
With the relay on, the NVR only ever talks to the virtual camera, and the throughput below can be measured. Turn it off to hand the NVR the upstream URL directly — lighter, but the real camera's address becomes visible and no bitrate can be reported.
Output codec
Re-encoding only happens when the source is not already the codec you picked, so choosing H.264 for an H.264 camera still costs nothing. A real transcode is expensive: software H.265 of a 4 MP stream will occupy several CPU cores per camera. Pick a hardware encoder if your host has one. On Automatic the bridge uses whatever it detected on this host (shown in the GPU badge at the top) and falls back to software if there is nothing; the right device is passed into the container for you. If the stream stays black after switching, drop the audio: not every camera's audio can be carried into RTSP.
Object detection
Runs on the sub stream, which is small enough to keep the cost down; without one it falls back to the main stream. Detection happens here, so it works with cameras that have no intelligence of their own. The findings are published as ONVIF events and only listed here.
Click to add or remove. person, vehicle and animal each stand for everything of that kind; name a single class instead to narrow it, for example car,truck,dog. A van has no class of its own because the model has none — a delivery van comes back as a car or a truck depending on its shape. Packages are absent for the same reason: there is no class for a parcel, and inferring one from "suitcase" would be a guess dressed up as a detection.
Measured on one machine at two threads: fast takes about 130 ms a frame, accurate about 475 ms — roughly four times the work, for a better answer on small and distant things, which is the case that matters outdoors. At three frames a second that is a third of a core against a core and a half, per camera. Built with --build-arg DETECT_GPU=1 and run on a host with the NVIDIA container runtime, both run on the card instead; the camera log says which it got.
A model asked twice about the same still picture does not always answer the same way: it will find a person in a hedge or a car in a pattern of shadows, hold that for a frame or two, and drop it. On a scene where nothing has moved, that is the only thing such a detection can be. With this on, a detection is only believed once that part of the picture has actually changed — movement anywhere during the sighting counts, so someone who walks in and then stands still is still reported. It is also what the CPU cost depends on. The comparison is made first and the model is not run at all on a frame where nothing changed, so a camera watching an empty yard costs about a millisecond a frame instead of a hundred, and only starts working when something walks into it. Something standing in view is re-checked every ten seconds, so a stream that freezes cannot leave motion stuck on. Turn it off for a camera watching something that genuinely never moves, such as a gate you want told about whether or not the car arrived while you were looking — at the price of running the model on every frame, all day.
Stills are what make the timeline worth opening: they turn a count into something you can check. One ffmpeg run and a few tens of kilobytes per detection, off the main stream. The disk they may take is set once for all cameras under Settings, and the oldest go first.
An object has to appear in several consecutive frames before it counts, which throws away the single-frame flickers a small model produces. After reporting, that type stays quiet for the period above, so one person walking past is one event. Motion itself is a state rather than a ping: it turns on when something is in view and off again once nothing has been seen for the hold time.
Findings are published as ONVIF events, which an NVR reads by subscribing to this camera. Each one goes out under several topic names, because no two products agreed on one: tns1:VideoSource/MotionAlarm and tns1:RuleEngine/CellMotionDetector/Motion for motion, tns1:RuleEngine/ObjectDetector/Object carrying the class, and tns1:RuleEngine/MyRuleDetector/PeopleDetect and its siblings for the clients that expect one rule per class. Nothing the model cannot see is advertised, so no filter in your NVR is left waiting on an event that never comes.
